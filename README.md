# INVIX — каталог товаров

Минимальный сервис каталога: администратор добавляет товар через Telegram-бота
(фото + название одним сообщением), изображение сохраняется в MinIO, запись — в
PostgreSQL, каталог смотрят на сайте Next.js или внутри Telegram Mini App.

## Стек

| Часть | Технология |
|---|---|
| Веб-интерфейс | Next.js 14, App Router |
| Backend | FastAPI (Python 3.12) |
| Telegram-бот | aiogram 3 |
| База данных | PostgreSQL 16 |
| Хранилище изображений | MinIO (S3 API) |
| Работа внутри Telegram | Telegram Mini App |
| Точка входа / балансировка | nginx |

## Архитектура

```
                ┌────────────┐
 браузер / ───► │   nginx    │ ──► frontend × N (Next.js, SSR)
 Telegram       │  (порт 80) │ ──► backend  × N (FastAPI) ──► PostgreSQL
 Mini App       └────────────┘         │                └──► MinIO
                                       ▲
                 бот × N (aiogram) ────┘  POST /api/products
                 (polling, Telegram сам раздаёт updates между репликами)
```

- Бот ничего не хранит: скачанное у Telegram фото уходит в backend, который
  пишет файл в MinIO и запись в PostgreSQL.
- Каталог — SSR-страница Next.js; картинки отдаются самим backend'ом
  (`/api/products/{id}/image` читает объект из MinIO и отдаёт байты), поэтому
  наружу смотрит только nginx, а MinIO публиковать не нужно. Работает и в
  браузере, и внутри Mini App без дополнительной конфигурации.
- Бакет MinIO создаётся backend'ом при старте (с ожиданием, пока MinIO
  поднимется), отдельный init-контейнер не нужен.
- Создание товара доступно только боту: запрос подписывается заголовком
  `X-Internal-Token` (общий секрет в env бота и backend).

## Запуск

```bash
cp .env.example .env          # заполнить TELEGRAM_BOT_TOKEN, TELEGRAM_ADMIN_IDS, MINI_APP_URL
docker compose up --build
```

По умолчанию поднимаются 2 реплики backend, бота и frontend; стек доступен на
`http://localhost:8080`.

Число реплик меняется в `docker-compose.yml` (`deploy.replicas`) или на лету:

```bash
docker compose up -d --scale backend=3 --scale bot=3 --scale frontend=3
```

### Проверка нескольких экземпляров

Все компоненты stateless:

- **бот** — без FSM и памяти процесса: любое фото с подписью от администратора
  создаёт товар; Telegram Bot API сам распределяет updates между поллерами;
- **backend** — состояние только в PostgreSQL и MinIO, локальный диск не
  используется;
- **frontend** — SSR без состояния, данные тянет из backend на каждый запрос
  (`cache: "no-store"`);

Образ MinIO — `pgsty/silo`. **Важно:** ТЗ требует MinIO (S3 API), и требование
выполняется: silo — форк MinIO Community с тем же S3 API, теми же переменными
окружения и поведением; backend работает с ним через стандартный S3 API, как с
MinIO. Замена касается только источника контейнерного образа: оригинальный
`minio/minio` удалён с Docker Hub в сентябре 2026, а quay.io/minio с 24.09.2026
требует авторизацию — стек на оригинальном образе сегодня не поднимается на
чистой машине. Если у проверяющего есть доступ к образу `minio/minio`
(локальный кеш или аккаунт quay.io), достаточно поменять `image:` в
docker-compose.yml — код менять не нужно.
- **nginx** — Docker DNS возвращает все реплики апстрима, nginx балансирует
  round-robin.

Проверка: поднять стек, добавить товар через бота, затем
`docker compose up -d --scale backend=3 --scale frontend=3` — каталог продолжает
отдаваться с любой реплики, товары и картинки общие.

### Smoke-тест живого стека

```bash
./scripts/smoke.sh http://localhost:8080
```

Проверяет страницу «Каталог», список товаров, запрет анонимного создания,
создание товара с токеном, появление в каталоге и редирект картинки в MinIO.

## Переменные окружения

См. `.env.example`.

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота из BotFather |
| `TELEGRAM_ADMIN_IDS` | id администраторов Telegram через запятую |
| `MINI_APP_URL` | публичный https-адрес каталога для кнопки Mini App |
| `INTERNAL_TOKEN` | общий секрет бот ↔ backend |
| `POSTGRES_*` | доступ к PostgreSQL |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` | доступ к MinIO и бакет |
| `HTTP_PORT` | внешний порт nginx (по умолчанию 8080) |

Для Mini App кнопка бота уже ведёт на `MINI_APP_URL`; чтобы открывать каталог
ещё и из меню бота, привяжите тот же URL в BotFather (`/setmenubutton`).

## Тесты

```bash
pip install -r backend/requirements.txt -r backend/requirements-dev.txt
pip install -r bot/requirements.txt -r bot/requirements-dev.txt
cd backend && python -m pytest tests -v
cd ../bot && python -m pytest tests -v
```

Backend-тесты гоняют API на SQLite (через тот же SQLAlchemy-код) с
in-memory S3, включая проверку, что два инстанса приложения на одной БД видят
один каталог. Bot-тесты покрывают сценарии бота без Telegram. Конфиг CI в
репозиторий не включён: тесты и smoke запускаются локально по командам выше.

## Решения по неуточнённым пунктам ТЗ

В ТЗ эти условия не определены, приняты следующие решения:

1. **Синтаксис команды.** `/start` и любое обычное сообщение — фраза
   «У меня есть товар» и кнопка Mini App. Создание товара: команда `/new` (или
   текст «Создать товар») — бот подсказывает формат, затем администратор
   присылает фото с названием в подписи одним сообщением. Фото с подписью от
   администратора создаёт товар и без `/new`.
2. **Назначение администратора.** Список id Telegram в `TELEGRAM_ADMIN_IDS`.
   Фото от остальных пользователей товар не создаёт — бот отвечает стандартной
   фразой с кнопкой каталога.
3. **Подтверждение создания.** Бот отвечает
   `Товар «название» добавлен в каталог (id: N)`.
4. **Формат фото.** Принимается именно `photo` (сжатое Telegram, JPEG), не
   `document`. Альбомы не обрабатываются: один товар — одно сообщение с одним
   фото. Ограничение размера — 10 МБ на backend (Telegram Bot API сам
   ограничивает скачивание 20 МБ).
5. **Раздача картинок.** Через backend (прокси из MinIO), а не presigned URL:
   presigned ссылка уводила бы браузер на адрес самого MinIO, который в
   общем случае не опубликован. Чтение объекта целиком допустимо при лимите
   10 МБ.
6. **Поля товара.** Только название и фотография, как в ТЗ; цены, категории и
   поиска нет.
7. **Кластеризация PostgreSQL и MinIO** в ТЗ не требуется — stateless
   относится к прикладным компонентам; данные в одной PostgreSQL и одном
   бакете MinIO общие для всех реплик.
